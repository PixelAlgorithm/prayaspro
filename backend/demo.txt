It connects student clients needing academic or lab project deliverables with verified student
specialists who earn stipends and verifiable peer ratings.

The platform is built on PostgreSQL 18 with high-dimensional vector embeddings, Express/TypeScript,
and a modern Next.js 14 frontend.

Key DBMS Level 3 concepts fully implemented include:
  1. 9 Normalized Relational Tables + 1 Vector Embedding Table matching our uploaded ER Diagram.
  2. ACID Transactions using PL/pgSQL stored procedures with row-level locks (FOR UPDATE)
     for atomic proposal acceptance and financial payout settlement.
  3. Database Triggers enforcing relational integrity (e.g., blocking self-applications and invalid statuses).
  4. Analytical Database Views avoiding Cartesian products via CTEs for student and marketplace metrics.
  5. Indexing strategy: B-Tree for FKs, Composite for status+deadline, GIN for full-text search.
  6. pgvector Semantic Search using the native <=> Cosine Distance operator over 384-dimensional
     unit vectors to match student skill portfolios with task requirements."

6. TOP 10 VIVA QUESTIONS & BULLETPROOF ANSWERS
====================================================================================================

Q1: Why did you choose PostgreSQL with pgvector instead of MongoDB or Pinecone?
A1: Three critical DBMS reasons:
    1. Financial payouts and contract state transitions require ACID compliance. PostgreSQL guarantees
       Atomicity, Consistency, Isolation, and Durability, eliminating double assignments or lost payments.
    2. Zero synchronization lag: Vector embeddings live in the SAME transactional engine as relational records.
       When a task or skill profile is updated, relational and vector data stay in lockstep without distributed sync errors.
    3. Hybrid querying: We can combine relational filtering (e.g. status = 'OPEN', budget >= 500)
       with vector similarity (ORDER BY embedding <=> query_vector) in a single optimized query plan.

Q2: How do you enforce a 1:1 relationship between Task and Assignment?
A2: In the 'assignments' table, the column 'task_id' has an explicit UNIQUE constraint:
    `CONSTRAINT uq_assignments_task UNIQUE (task_id)`.
    This guarantees at the database level that a task can have at most ONE active or final contract.

Q3: How do you prevent race conditions when multiple users apply or when an owner accepts?
A3: We implement the PL/pgSQL stored procedure `fn_accept_application_transaction` which issues:
    `SELECT status FROM tasks WHERE task_id = v_task_id FOR UPDATE;`
    The `FOR UPDATE` clause places an exclusive row-level lock on the task row, serializing concurrent
    transactions and preventing two applicants from ever being accepted simultaneously.

Q4: What is the <=> operator in pgvector?
A4: `<=>` is the native PostgreSQL Cosine Distance operator.
    Cosine Distance d = 1.0 - (A . B) / (||A|| * ||B||).
    Since our 384-dimensional embeddings are pre-normalized to unit length (L2 norm = 1.0),
    the cosine distance simplifies to `1.0 - dot_product`, enabling sub-millisecond similarity lookups.

Q5: Why use Common Table Expressions (CTEs) in 'view_student_performance'?
A5: A student has multiple skills (1:M), multiple applications (1:M), and multiple reviews (1:M).
    If we directly JOIN all these tables in a single SELECT query, it creates a Cartesian product explosion,
    multiplying review counts and distorting earnings totals.
    We isolate aggregations into independent CTE subqueries per dimension before joining to 'users'.

Q6: How do you prevent students from applying to their own tasks?
A6: Through a BEFORE INSERT database trigger: `trg_prevent_self_application`.
    When an INSERT on `applications` is executed, the trigger compares `NEW.student_id` with `tasks.owner_id`.
    If they match, it raises an exception (`RAISE EXCEPTION`) and aborts the insert at the schema level.

Q7: What indexes did you build and why?
A7: 1. B-Tree indexes on all foreign key columns to speed up relational joins.
    2. Composite B-Tree index on `tasks(status, deadline)` to optimize marketplace searches.
    3. GIN (Generalized Inverted Index) using `to_tsvector('english', title || ' ' || description)`
       for fast full-text searching across project descriptions.

Q8: What stored functions did you write?
A8: 1. `fn_calculate_student_rating(user_uuid)`: Dynamically computes average rating and review counts.
    2. `fn_calculate_student_earnings(user_uuid)`: Aggregates settled payments where `payment_status = 'SUCCESS'`.
    3. `fn_accept_application_transaction(...)`: Handles atomic contract formation.

Q9: What is the purpose of the 1:M relationship between Categories and Tasks?
A9: Each task belongs to exactly one category (`categories.category_id` FK in `tasks`), enabling
    categorical partitioning, domain indexing, and category-level statistical views (`view_task_marketplace_stats`).

Q10: How does your frontend communicate with the database?
A10: The Next.js frontend uses Next.js server rewrites to proxy API requests to our Node.js/Express
     backend on port 5000. The backend utilizes a PostgreSQL connection pool (`pg.Pool`) with parameterized
     queries to prevent SQL injection vulnerabilities and maintain persistent database connections.
